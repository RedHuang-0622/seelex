## 1. 结论

**成立（按 §8.3 的回滚条件）。** 两条硬判据（1 墙钟、5 进程表/目录）都过，软判据 2、4 过，
软判据 3（总 prompt ≤ A×1.10）不过——实际是 **+158%**。

一句话：**轮询这个形状合法、不破前缀缓存、能把"不必等结果"的那一类回合从 23 秒压到 4.9 秒；
代价是每个额外轮次都要重发一遍信封，所以"任务本身要求立刻拿到结果"时墙钟几乎不省，而 token
名义成本明显上涨。** 因此切片保持默认关（`limits.async_exec.enabled=false`），打开它应该按
"命令时长 × 是否有可并行的活"来决策，而不是当通用开关。

## 2. 方法与一次有意的偏离

两臂只差一个字段：`limits.async_exec.enabled`。装配、账号、模型、工具面、任务素材、提问
措辞全部相同（`newFullChainHarnessWithLimits`，`async_exec_ab_live_test.go:186`）；provider
前挂录制反向代理，逐条记录真实请求体与 `prompt_cache_hit_tokens`（复用
`real_api_prefix_live_test.go` 的代理与全链路装配）。每个任务每臂各 3 次取中位，A/B 交替跑，
让 provider 抖动与机器负载同时作用于两臂。

**偏离 §8.4**：原文要求基线从干净提交点用 `git worktree` 拉副本，理由是"另一会话有在飞的
前端/皮肤改动未提交，混进 A/B 会污染对比"。该前提已消失——前端那批改动同日已提交为
`973bb80`，工作树里未提交的只剩本切片自身。改用**同一二进制内翻开关**作 A 臂，对照更严格
（同进程、同机、同时间窗、逐字段同装配），且避免两次构建引入编译器/依赖差异。代价是 A 臂
仍然链接了切片代码（关闭态为死代码），因此**编译产物体积、未使用的登记表内存**这类差异不在
本次度量范围内——它们也不属于 §8.3 的五项判据。

样本任务的降级：§8.3 原文写"构建 + 测试并行""跑一次真实冒烟的同时改文件"。为可复现与成本，
用 `sleep 20; echo SENT-*` 代表长命令、`read_file`/`write_file` 代表并行的活。**这把"长命令"
的时长固定成 20 秒且去掉了真实构建的方差**，所以墙钟差值可信、绝对值不代表真实构建场景。

指标 4 的判据只看 wire：标记 `SENT-*` 只存在于命令输出里，必须出现在 `role=tool` 消息中，
且出现在 `async_output` 调用**之后**的那次请求里才算数。受理回执不含输出，模型抄不到。
T3 以"不取回结果"为设计目标，其指标 4 降级为"至少完成一次 `async_output` 调用"（表中已单列）。

## 4. 逐轮并排（T1 第 3 次，差异行标注）

A 臂（关，同步阻塞）：3 次 provider 请求，墙钟 23.24 s，prompt 13373，未命中 701。

B 臂（开，受理回执 + 轮询）：7 次请求，墙钟 22.32 s，prompt 34532，未命中 1508。

| 轮 | prompt | cached 比率 | 说明 |
|---|---|---|---|
| r1 | 4477 | 0.94 | 与 A 的差异只在工具 schema（多 `background` + `async_output`，**+213 token**） |
| r2 | 4660 | 0.96 | **diff**：派发秒回受理回执（`state=running`，不含输出） |
| r3 | 4786 | 0.96 | **diff**：趁命令在跑读 a.txt/b.txt |
| r4 | 4946 | 0.96 | **diff**：`async_output` 第一次取回 → running |
| r5 | 5082 | 0.96 | **diff**：第二次取回 → finished + 标记 |
| r6 | 5218 | 0.96 | 作答 |
| r7 | 5363 | 0.95 | 收尾 |

两臂并排的结论：

1. **B 臂每一轮的命中率都不低于 0.94**，随历史在尾部生长而稳定爬升（0.94→0.96→0.96→0.96→0.95）
   ——轮询没有作废任何已定稿前缀，与 §0 的 P7 一致；对照 P3（中段改写字母级差异即塌到 0.25）。
2. 成本长在**轮次数量**上，不在单轮：B 比 A 多 4 轮，每轮多带 130–250 token 的增量正文，
   但每一轮都要把 ~4700 token 的信封重发一次，于是 `prompt` 相加从 13373 涨到 34532（+158%）。
3. **同一件事用未命中字节量才看得清**：A 未命中 701，B 未命中 1508，**真实新增 807 token**
   （≈每多一轮 +202）。名义 +21159 里有 20352 是命中折扣部分。
4. 冷启动口径（重要）：两臂工具 schema 不同 ⇒ 缓存前缀不相交，**每套 schema 的首个请求**
   必付一次冷 miss。本表看不到它，是因为更早的校准轮已经把两套前缀各自写进了缓存——校准轮里
   B 臂 r1 曾测出 0.09（对照 A 臂 r1 的 0.93），差点被误读成"轮询破缓存"。判"轮询是否破前缀"
   必须看轮内序列，不能拿单点比率。

## 5. 判据 3 不成立意味着什么

阈值是"总 prompt ≤ A×1.10"，实测 +158%，按字面就是不成立。拆开看它抓的是什么：
**信封重发 × 额外轮次**。可压缩的方向有三个（都不需要改协议）：

- 减少取回次数：`wait_ms` 现在默认 5 s，T1 里模型连查两次才拿到结果。让**取回等到终态**
  （`wait_ms` 贴近命令时长，或提供 `wait_until_done`）就能把 B 的 7 轮压到 5 轮。
- 增量交付已经生效：单次取回上限 4000 字符 + 游标，日志不会被重播（`log_bytes` 每次 +19，
  即命令真实输出）。
- `background` 与 `async_output` 两个 schema 常驻的固定成本只有 +213 token/轮，占比小。

**不改判据、也不事后放宽**：本轮结论就是"硬判据过、成本判据不过"。是否继续投入取决于第 3 节
的取舍——如果只用在不等待结果的形状（T3 类），+158% 的绝对值很小（807 token）；如果当成
通用异步化，token 名义成本会一直挂在账单上。

## 6. 顺带查掉的两件事（有实测，不是推断）

### 6.1 竞态：确实存在过，已修并留了反证

旧形状：`asyncRegistry.begin` 返回表内 `*asyncRun`，派发侧在锁外做整结构体拷贝
（`renderAccepted(*run, …)`），而执行体收尾时 `finish` 在 `g.mu` 内改写同一条目的
`state/exit`——同一块内存、一侧在写、没有共同的锁。

- **反证**：`seelebridge/tools/async_exec_raceproof_test.go`（tag `raceproof`，opt-in，
  永不进 CI）逐行复刻旧口径，`go test -tags raceproof -count=5 -race` **实测报出
  `DATA RACE`**（写=收尾改 `state/exit`，读=锁外拷贝），`_logs/raceproof_run.log`。
- 为什么日常 `-race` 抓不到：窗口只有"回执正在拷贝"撞上"命令恰好这一瞬结束"，
  此前的 `-race -count=3` 未复现，故一度只能报"潜在"。
- **修法**：`begin` 与 `snapshot` 同口径按值返回副本（`async_exec.go:105`），
  `startAsync`/`renderAccepted` 改收件值。回归钉在
  `TestAsyncRegistryBeginHandsOutACopy`——回执渲染的是派发那一刻的状态，命令同瞬间结束
  也不回头改写它。
- 修后：`go test ./seelebridge/tools/ -race` 全绿。

### 6.2 泄漏：进程级目录此前无人回收，现已闭合

- 修复前现场：临时目录里 **44 个** `seelex-async-*`，每个是一次进程/装配留下的输出目录，
  没有任何代码路径会删它（驱逐只删单条记录的文件）。
- 修法（三条，缺一不可）：① `Router.CloseAsync` + `asyncRegistry.close` 在
  `registerProjectScopedTools` 里登记进 `Runtime.Shutdown` 的逆序关停链
  （`runtime_tools.go:163`）；② close **当场试删**，删不动（执行体还握着日志句柄，
  Windows 下必然失败）就记下关停意图，由**最后一条 `finish` 补删**——那一刻文件已关闭，
  是唯一确定的可删点，不排定时器也不按"多久算陈旧"猜；③ 关停后 `begin` 直接报错，
  否则会新建一个再没人回收的目录。
- **实测闭合**：隔离跑一次 B 臂回合（`T2/B`，命令 5 s）前后，临时目录数 **49 → 49**；
  全量矩阵的 9 个 B 回合各 +1 个目录（运行期），进程收尾后无净增。矩阵期间观测到的
  +5 经逐目录内容核对，全部来自**同一时刻跑的一轮单元测试**（`a1.log` 里的
  `owner-only-marker` / `incremental-marker` / `ack-payload-marker` 是单测 fixture）。
- 测试自己也在漏，现已归零：脚手架挂 `t.Cleanup`（`asyncTestRouter` /
  `newAsyncRegistryForTest`），派发型用例另外要**等执行体收尾才退出**
  （`waitAsyncTerminalForTest`——终态是 `awaitAsync` 关掉文件之后才合成的，等到它才是可删点）。
  连续两轮 `go test ./seelebridge/tools`（含 `-race`）临时目录 **59 → 59 → 59**；
  修之前是每轮 +2，再往前每轮 +5。补删那条分支由
  `TestAsyncRegistryCloseSweepsLateFinish` 钉住（Windows 才走得到，别处 close 当场删掉、
  用例仍通过）。
- 18/18 样本 `leftover=0`：命令过了自身期限 + 10 s 宽限后，`sleep.exe` 计数不增，无孤儿进程。
  30 分钟硬超时是**只杀 bash、不杀其子进程**的形状，本轮样本未覆盖那条路径（`sleep` 是
  命令的唯一子进程且已自行结束）——如果将来要主张"硬超时也不留孤儿"，需要另设样本。
