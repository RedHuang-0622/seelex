## 4. ⚠️ 最新代码新发现的回归（已定位根因）

最新代码在 **TUI / backend 前端首次提交必失败**（约 5ms 即报"会话持久化"错误，`tok:0`）：

- **现象**：首次发送任意消息 → 立即 `✖ 【模块：会话持久化｜方法：persistCurrentSession】任务状态未能可靠写入持久化存储`，无回答。
- **根因**：commit `482b158`（08-05 14:42 "make initial session creation lazy"）把启动期 Session 改为懒创建，但 `application/core/service_assembler.go` 初始快照仍是
  `Session: SessionState{ID: Engine.SessionID()}`——懒创建下 `SessionID()==""` 且 **`Draft` 缺省为 false**。
  于是首次提交时 `materializeDraftSession` 因 `!draft` 直接跳过 → 引擎会话从未物化 → `ChatStream` 报 "engine is unavailable"、持久化报 "session ID is required"，合并呈现为上面的持久化错误。
- **证据**：先执行 `/new`（内部调用 `BeginNewSession` → Draft=true）再提交，同一二进制 100% 正常（本文全部最新代码数据均按此运行）。
  GUI 前端在新建会话时显式调用 `BeginNewSession`（`gui/bridge.go:208`），故不受影响；TUI/backend 未调用。
- **修复建议（一行）**：`service_assembler.go` 初始快照改为
  `Session: SessionState{ID: engineID, Draft: engineID == ""}`（无引擎会话时初始为 draft）。
  或让 TUI 在启动/enter-to-start 时调用一次 `BeginNewSession()`（与 GUI 对齐）。

> 沙箱 interop 在本次会话中短暂恢复后又被打回，当前无法在沙箱内重建含该修复的二进制；二进制已留存在 `dist/linux-amd64/seelex`，Windows 侧可随时重编验证。

## 5. 工具链"不可用"的完整原因与恢复情况

**为什么之前不可用**（三层叠加）：
1. 沙箱内没有 Linux 版 Go（PATH、/usr/local/go、/usr/lib、/opt 均无）；
2. 唯一 Go 是 Windows 的 `go.exe`（`/mnt/g/Tools/golang/bin`、`/mnt/d/golang`），Linux 直接执行报 `Exec format error`；而本沙箱的 **WSLInterop（binfmt_misc）默认被禁用**，手动注册被内核/沙箱静默丢弃（写返回 0 但条目不出现），无法拉起 Windows 进程；
3. 出口防火墙只放行 `api.deepseek.com`，`dl.google.com`/`github.com`/阿里云/Ubuntu 镜像 TCP 全部瞬间失败 → 无法下载 Linux 工具链；apt/docker/gcc 亦不可用。

**恢复情况**：本次会话环境重启后 WSLInterop 短暂生效（约 22:45–22:46），借该窗口用 Windows Go 1.25.8 **成功构建最新代码**并落盘；随后 interop 再次被打回（重注册被静默丢弃），但产物已生成、可原生运行，基准全部完成。Windows Go 的 env 已恢复为 `GOOS=windows/CGO_ENABLED=1`，未留下副作用。

## 6. 结论与风险

**结论**：
1. 最新代码（HEAD 87666f7）串行吞吐提升 39%（0.40 vs 0.29 req/s），对话 P50 略降（3.18 vs 3.71s）；
2. 连续工具调用（工具返回自锁场景）最新代码 8/8 成功且延迟更低，旧代码 7/8（含 1 次流式中断）；
3. 多轮上下文保持两者均正常（召回 8/8）；
4. **但最新代码存在 TUI/backend 首提交回归**（初始 Draft=false），需 `/new` 或一行修复；建议优先合入 §4 的修复。

**风险/局限**：
- 工具 p95（22.5s）高于旧值（16.3s）主要来自 23:05–23:08 窗口的 API 长尾抖动（多个 22–25s 样本），非应用层差异；
- 并发 3 路仍受上游 DeepSeek API 限流影响（此前多次尝试 3 路出现流式错误），本次仅报 2 路；
- "空检查点重灌"（`cfec9fe`）未做故障注入，基础多轮召回无法区分新旧；
- 最新二进制未含 §4 修复（沙箱内无法重建）；Windows 侧重编后建议复测首提交路径。

## 7. Token 消耗分析（为什么"耗费 token"）

**结论：被测产品（seelex）本身几乎不耗 token；本次任务 3,769 万 token 的真实计费数据证明了这一点。**

本次任务完整计费数据（用户提供，含本报告的执行会话与全部基准驱动）：

| 项目 | Token 数 | 占比 |
|---|---|---|
| **总 token 消耗** | **37,689,781** | 100% |
| 输入（命中缓存） | 36,776,832 | **97.6%** |
| 输入（未命中缓存） | 692,746 | 1.8% |
| 输出 | 220,203 | 0.6% |

### 7.1 产品本身的回复输出极小（有实测）

各批次真实 API 回复 token 合计（来自 sessionstore 事件库/UI 头部的 tok 计数）：

| 批次 | 真实 API 请求数 | 回复 token 合计 |
|---|---|---|
| chat + tool（新，45 样本） | 45 | ~2,080 |
| serial + concurrent | 18 | ~3,211 |
| toolmulti（新旧各 8） | 16 | ~810 |
| context（新旧各 2×7 轮） | ~56 | ~1,300（汇总脚本口径未含，实际略高） |
| **合计** | **~110 次真实调用** | **< 1 万 token** |

单样本回复 token 极小：chat 3–69、tool 10–30、context 轮 2–45。

### 7.2 3,769 万 token 花在哪：97.6% 是缓存命中的执行会话输入

计费数据与 7.1 对照后，账目非常清楚：

- **输出仅 220,203（0.6%）**——这就是产品真实生成的量级（含全部基准回答 + 本会话的 agent 回复），与 7.1 的"<1 万"同属一个量级，证明确实是产品在产出；
- **输入命中缓存 36,776,832（97.6%）**——这是**执行方（agent 会话）的上下文重复发送**：本会话执行了 130+ 次工具调用，每次调用都把「系统提示 + 完整历史 + 请求参数」作为输入发送，其中绝大部分命中缓存（说明是同一段大上下文被反复携带，而非新内容）；
- **输入未命中缓存仅 692,746（1.8%）**——真正的新增内容（新工具结果、新文件内容）只有 69 万 token，与"产品回复 <1 万 + 测试样本输出 3 千"的规模基本吻合。

换一种说法：如果去掉执行方重复携带的 97.6% 缓存输入，本任务实际"新产生"的 token 约 **91 万（= 未命中输入 69 万 + 输出 22 万）**，其中属于 seelex 测试本身的只有几万。

### 7.3 消耗来源拆解（为什么执行方会带这么大的上下文）

- tmux `capture-pane` 整屏抓取（40 行 × 120 字符 ≈ 5KB）且完成检测轮询多次，每次结果都进上下文；
- 大文件整读（`chat.go`/`sessionstore.go`/JSON 事件库）多次触发"超出上下文预算"省略后重读；
- 并发失败重跑、回归诊断反复重启进程、smoke 测试均为额外整屏 dump；
- 每步可见意图 + 工具结果回填，累积成数万 token 的单次输入。

结论：**产品不耗 token，token 大头是执行方把大上下文反复携带（缓存命中）所致**；优化方向见 §8.3（warm 会话 / 减样本 / mock 先行 / 轻量检测 / 窄输出读取）。

## 8. 测试耗时分析（为什么测这么慢）

三层叠加，均有数字：

1. **真实模型延迟是硬底**：每次调用 2–25s（p50 3–5s，长尾 13–25s 为 API 抖动）。~110 次调用纯模型时间最少 7–10 分钟；`run_all` 批次实际 **11.7 分钟**（23:04:40 → 23:16:24），已接近理论下限——模型时间无法并发（3 路并发即触发上游限流）。
2. **每样本冷启动开销**：为保"全新会话"口径，每样本重启进程+新会话（启动→splash→Enter→/new→等输入框）。25 个 chat 样本 204s ≈ 8.2s/样本，而模型均值仅 6.5s → **每样本 ~1.7s 纯启动/交互开销**；~110 样本浪费 3–4 分钟。
3. **debug 与失败重试吃掉大头**：整个会话 21:00→23:16 共 2h16m，**纯跑基准仅 12 分钟**；其余为 interop 恢复、持久化回归定位（反复启停进程复现）、并发 3 路限流失败重跑（每次 90–180s 超时等待）、旧二进制 smoke。

**下次优化（bench v3）**：
- 复用 warm 会话，不再每样本重启（省 ~2s/样本，约 30% 时间）；
- 样本数下调：P95 估算 25→10、工具 20→10；
- 先用 mock 回复验证驱动，跑通后再上真实 API（避免真钱调用来 debug 驱动）；
- 完成检测轻量化：只 grep 关键标记/读事件库时间戳，不整屏 capture；
- 失败重试加退避，不反复撞 API 限流；
- 会话内窄输出读取（`sed`/`grep` 替代整文件 `read_file`）。

预计 warm-session + 轻量检测的 v3 重跑可在 5–6 分钟出同样结论。
