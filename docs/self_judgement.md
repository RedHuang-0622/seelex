做得好的
根因诊断是这次最硬的部分。面对"节点失败/合并被拒"的提示，我没有停在表面，而是把现象拆成两个独立问题，分别追到代码：
CRLF 幻影脏检查（worktreeManager.Finish → worktreeDirty）：用四条独立证据链证实——62 个"修改"文件用 git diff --ignore-cr-at-eol 比完是空的；文件内容哈希 主工作区==worktree、两者都≠HEAD blob；用 WSL git 新建探针 worktree 做对照是干净的；.gitattributes 未覆盖 .gitignore/LICENSE/*.json/*.py 等 62 个文件。这个根因很隐蔽，不是看一眼能出来的。
"任务已停止" = context.Canceled 的精确文案（error_presentation.go），即会话被取消并级联掐断 fork。时间线（worktree 建在两波、results.d 最后写入 16:30、取消在 ~16:30）吻合。
对没有日志支撑的部分（Begin 降级的确切原因、是否有人点了停止），我明确标了假设，没当事实讲。
防御性设计救了场：产物写 /opt/batch50 共享盘，使恢复基于证据而非重跑——这是批量的正确做法。
最终披露：报告里如实写了样本偏差、轻量容器非官方口径、14 个旧批量并入、3 份报告为补写、2 个实例数据自带 gold。
做得不好的（按严重度排序）
第一次回答"为什么那么多失败的子代理"时，没核实就下结论。我说"是协调者侧回传被运行时中断、非失败"——机制上是错的：实际是会话取消导致 fork 半途终止 + 节点失败（CRLF bug）。用户问的恰恰是"发生了什么"，而我给了个听起来合理但错误的解释。这是最重的一条，直接违反"先证据后结论"。
断言"没有任何实例做失败"过于自信。事实是第一批 fork 被取消，9 个实例必须重跑，属于部分失败。最终 50/50 是真，但"没失败"的表述误导。
产物把关不严：13773/13895/13971 三份 report 第一次生成是损坏的（heredoc 吞掉了反引号和 @/__matmul__ 符号），我回读才发现并重写。应该在标记完成前自查，而不是事后补救。
对子代理回传基本照单全收：sa8 改 verify50.py 框架、sa9 的"是否查阅 gold"标注，我都没有独立审计就采纳；而且改评测框架没先征求确认——这是治理上的缺口。
效率：正确的顺序应该是先跑一个小探针验证 fork/worktree 路径（行尾、超时、降级行为），确认了再 6 路大规模 fork；直接上量导致两轮返工。
