# A2A「Agent Team Work」实际作用评鉴（2026-09-16）

**问题的直接回答**：现在这套东西**有真实但有限的作用——它买到的是"看护"，不是"团队干活"**。
具体说：三件事有实证价值（逃生天花板、一次独立上下文的对抗评审、角色权责隔离的骨架），
两件事目前**没有**实际作用（"多员工并行产出"、"更强的结果"），因为它根本还没有第二个
执行体在干活。要让"team work"名副其实，缺的是**执行体**和**可执行验证**，不是更多角色名。

本报告分三部分：① 代码事实（可复核）② 外部对照证据（标注可信度）③ 结论与建议。
**可信度口径**：`实测`= 本仓库代码可复核的事实；`强证据`= 公开对照实验/官方一手数据；
`中证据`= 受控比较但样本或口径受限；`弱证据`= 小样本/自报；`判断`= 我的推论。

## 一、代码事实：这个"团队"到底有几个执行体（`实测`）

| # | 事实 | 证据 |
|---|------|------|
| 1 | 治理循环的 EXEC 座位**不干活**：`execAct` 返回空 `TurnAction`，座位只用于推进轮次 | `application/core/goal_coordinator.go` `newGovernor`（`execAct := func(...) { return govern.TurnAction{}, nil }`） |
| 2 | 一轮里真正发生的 AI 调用只有 ADVISOR 回合；它= **一次无工具的 completer 调用** | `application/core/goal/techleader.go` `RunEval`/`runRoundLocked`；`seelebridge/runtime_goal_tl.go`（evaluator 只发一条 system+user 消息） |
| 3 | ADVISOR **看不到主会话原文**：输入是渲染出来的 `TLSessionEmbed`（goal 锚点 + 追加帧 + 最多 8 条自身回合摘要） | `application/core/goal/advisor.go`（`TLSessionEmbed`、`MaxEmbedRounds`、`RenderText`） |
| 4 | 该 embed 是**进程内**状态（不落盘）：重启即空；跨 goal 复用与否取决于 peer 是否被 reap | `advisor.go`（`AdvisorSession` 字段）；`techleader.go` `unbindIfTerminal` |
| 5 | 除 `tl` 外**没有角色回合执行面**：`needsRoleSession` 只排除 user/main，可唯一真正跑回合的是 TL；权限门注释自述"只有 tl 的 ADVISOR 回合，且它不持工具" | `application/core/agentteam/spec.go`；`main.go`（修复前的 `SetRoleSessionPolicyResolver` 注释） |
| 6 | 环的"逃生"= 轮次/无进展上限，而不是任务分解或并行调度 | `application/core/agentteam/runtime.go`（`StopRoundLimit`/`StopNoProgress`/`StopNoExecutor`/`StopEmptyRing`、`NoteTurn`） |
| 7 | 角色会话号 = `teamID-roleName`，**不含主会话身份**；注册表按主会话存储 | `application/core/agentteam/spec.go`；`sessionstore/team_registry.go` |

**由 1–7 推出的结构判断**（`判断`）：当前形态不是"多智能体协作"，而是
**单执行体 + 一个上下文被刻意隔开的评审者（ADVISOR） + 一个确定性的循环天花板**。
被命名为"员工/座位"的角色里，只有 `tl` 有回合实现；其余角色是**说话权**（环里的发言位）
而不是**做工权**（执行面）。

## 二、外部对照证据：多智能体在什么条件下才真的有用

### 2.1 等预算对照：同质多 agent ≈ 单 agent，但更贵（`强证据`）
- **MA-Evolve《At Equal Inference Cost, Multi-Agent Structure Does Not Beat a Single Frozen Agent》(arXiv 2609.04217, 2026)**：
  固定"语言模型调用总次数"后，完整 Planner-Executor-Critic 团队在 ALFWorld 上
  **0.769 vs 单 executor 0.754，p = 0.80（不显著）**，而团队多用了约 **1.8×** 评估调用；
  给 2–3× **免费**算力时团队才追平。
- 含义：**"角色"如果只是同一个模型换提示词、且共享同一条信息通道，那它买不到能力，只买到开销。**
  本仓库的 ring 恰好是这个形状：同一个模型、ADVISOR 只多拿一份被压缩过的摘要。

### 2.2 厂商一手数据：增益来自"并行广度"，不是"角色分工"（`强证据`）
**Anthropic《How we built our multi-agent research system》(2025-06-13)**
- 多 agent（Opus 4 主 + Sonnet 4 子代理）在其内部 research eval 上比单 Opus 4 高 **90.2%**；
  成本约 **15×** chat 的 token；BrowseComp 上**token 用量单独解释 80% 方差**。
- 原文同时明确：**多数编码任务的可并性子任务更少**，多 agent 主要适合"广度优先检索 /
  信息超出单上下文 / 大量复杂工具"；并建议子代理的产出**写文件系统、只回传轻量引用**，
  以避免"传话游戏"和 token 复制开销。
- 含义：本设计的 ADVISOR 不是"并行广度"，它是**串行的一次评审**——增益上限是"抓到一个
  执行者自己没发现的错"，不是"更快覆盖更多信息"。

### 2.3 反方工程论述（`判断`，作者为 Devin 团队，无对照数据）
**Cognition《Don't Build Multi-Agents》**：两条原则——① 共享完整上下文与完整 trace，
② action 携带隐式决定，冲突的隐式决定必然产出不一致结果；作者判断 2025 年多 agent
协作只会得到脆弱系统，建议单线程线性 agent + 专门的上下文压缩。
- 注意：本设计的 ADVISOR **刻意不共享**上下文（只看摘要）——这恰好避开了 Cognition 的
  "半成品被并行拼接"的坑，但代价是**它无法验证**（见 2.5）。

### 2.4 最危险的失败模式：互相背书（`强证据`）
- 多 agent 讨论会出现 sycophancy/confomity：**先于正确结论收敛**，准确率可低于单 agent 基线；
- 而**一名结构化异议者**能大幅降低被同伴压力带偏的概率（研究汇总口径：54–73 个百分点）。
- 含义：**"一个独立的、被鼓励说不的评审者"本身就是有依据的用法**——这是本设计里最站得住的部分。
  但它要成立有个前提：异议者得有**独立的信息源或可执行的验证**，否则只是"另一个观点"。

### 2.5 增益的真实来源：可执行验证与信息隔离（`强证据`）
- 对照实验里真正稳定的增益来自：独立并行探索（检索/超单窗）、多视角对抗审查、
  独立模块并行、**可执行验证接地**（跑测试/编译/复现）；负收益来自：顺序化任务、
  同文件编辑、强耦合编码、仪式性角色扮演。
- 映射到本设计：ADVISOR **既无工具也无验证手段**，它读的是一段渲染文本 →
  它的裁决是**似真性判断**，不是证据判断。这让"评审"环节的价值打了折扣。

### 2.6 A2A 协议本身（`中证据`+`判断`）
- A2A 已进入云厂商文档级支持（AWS/Microsoft），但**缺可验证的生产收益案例**；
  从业者讨论里"过度工程/没有用例"与"公司在用但难管"并存。
- 关键反例：**同宿主内的多 agent（Claude Code 的 agent teams）根本不用 A2A**——
  用文件邮箱 + 共享任务表。
- 含义：**A2A 解决的是"跨进程/跨厂商 agent 互操作"**，不是"同一个进程里让几个角色轮流发言"。
  本项目在自己进程内实现 A2A 形状的互操作，收益主要落在**可观测/可审计**，不落在能力。

## 三、结论与建议

### 3.1 有实际作用的部分（建议保留）
1. **逃生天花板 + 收口**（`实测`+`判断`）：确定性上限（轮次/无进展）防止自循环烧钱，
   且"逃生=这一轮 goal 结束"是干净可解释的语义。**这是本设计性价比最高的一块**——
   它的收益不依赖模型能力，是纯工程收益。本次已补齐"逃生即收口 + 归档 b 历史"，
   否则 loop 停了、goal 还挂着，用户只看到面板恒 0 轮。
2. **一次独立上下文的对抗评审**（`强证据`支撑方向）：ADVISOR 与执行者**不共享完整上下文**，
   规避了"相互背书"的主要通道；证据支持"结构化异议者"的价值。
3. **角色权责隔离的骨架**（`实测`+`判断`）：一旦有角色真的跑工具，"角色会话→权责→主体类"
   这条链就是**可审计的授权边界**（本次已把归属解析从"当前视图会话"改成按角色会话号，
   并加了失败即最严的口径）。这是安全资产，不是能力资产。

### 3.2 目前**没有**实际作用的部分（建议要么补，要么别宣称）
1. **"员工/团队并行干活"**：没有第二个执行体。座位名与角色名容易让用户以为有团队在做工。
   建议二选一：(a) 实现角色回合执行面（员工自己带工具跑一轮）；(b) UI 口径改成
   "评审/看护"，不要用"团队协作"的叙事。
2. **"多智能体比单 agent 更强"**：等预算对照不支持同模型换角色的增益（2.1）。
   本设计的额外开销是每轮一次 ADVISOR 调用，收益只在"真抓到了错"时兑现——
   目前没有度量证明它抓到了。
3. **A2A 协议互操作**：进程内自用不需要 A2A（2.6）。

### 3.3 让"team work"真正有用的四步（按性价比排序）
1. **给 ADVISOR 上工具（只读）**：`read_file`/`grep_search`/跑测试/看 diff。
   证据（2.5）显示增益来自"可执行验证接地"；这一步把裁决从"观点"变成"证据"，
   并且天然需要**已经做好的权限拦截**（readonly 主体类）——两件事在这里合流。
2. **只在值得的任务上开**：审查/审计/宽面检索开；顺序化编码、同文件强耦合改动别开
   （2.1/2.2 都指向这个结论）。默认常开 ring 是负期望。
3. **量起来再决定**：用已有的轮次/帧/回合统计做 A/B——同一批任务跑"开 ADVISOR / 不开"，
   记录 token 与结局。没有这个数，任何"有用"都是叙事。
4. **要跨进程/跨厂商互操作再投 A2A 协议**；进程内继续用共享任务表 + 轻量引用（2.6）。

### 3.4 一句话
> 现在这套不是"多智能体团队"，而是"**带确定性逃生天花板的单执行体 + 一个上下文隔离的评审者**"。
> 它值钱的地方是**看护（逃生/审计/权责边界）**，不值钱的地方是**宣称的团队产出能力**。
> 补上"评审者可执行验证"与"度量"，它就会从"有仪式感的角色扮演"变成"有实际作用的对抗审查"。
