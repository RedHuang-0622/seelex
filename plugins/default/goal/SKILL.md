# goal：目标看板 + V 模型派活

goal 不再是一排轮流发言的座位，**不再有席位轮转**。goal 是两件事：

1. **你自己的目标看板**——目标状态 + 完成条件 + 每阶段打点，跑在上下文里的固定位置。
2. **团队作业面的驱动口径**——你（主代理 = leader）按 V 模型阶段派活，用 `$teamwork` 的工具面执行，
   阶段收尾读证据、写里程碑、回填看板。

goal 由**提示词 + 团队作业面**驱动：没有框架侧的座位循环在推你，也没有第二套进度真相。

## 1. 看板（唯一的进度事实）

看板是**你自己总结的**目标视图，**不是复述用户原话**，也不是把用户的每句话照抄成条目。

- **内容**：目标正文（一句话写清「做完是什么样」）、完成条件（可验证）、阶段与右腿验证的配对、打点流水。
- **打点**：**每个阶段结束**在看板上追加一条打点：`阶段 id + 结论 + 证据锚点（命令/文件/提交/截图）+ 未决项`。
  不写流水账，不写「正在努力」这类无证据条目。
- **改写**：证据推翻原假设时**改看板**——改写目标正文 / 完成条件，并附一条 `decision` 打点说明
  「改了什么、为什么改、哪些阶段要返工」。目标内容随事实演进，是看板的正常动作，不是异常。
- **禁止**：不要再手写 `[GOAL] 进度: 2/5` 这类文本块——进度就是看板上的打点序列，位置让给看板本身。

### active seq 与看板位置（唯一口径）

- **active seq = 看板的活跃序号**：它指向看板上**当前焦点条目**（正在推进的那个阶段打点）。
  它的取值**不是用户消息的编号**，也**不是对用户原话的复述编号**；它是你对目标推进次序的自总结。
- **谁写**：只有 leader 写。**每阶段收尾时**（读完证据、写完里程碑之后）前移一次；
  阶段没有实质推进时**不动 active seq**，看板不打空点。
- **位置不变**：看板在上下文里由 `active seq` 钉在一个**固定位置**；位置一旦钉住就不再移动。
  每次打点只**改内容**（正文/完成条件/打点/焦点），**不换位置、不新开第二块看板**、不把旧看板复制到别处。
- **自检**：任何时刻读看板都应能回答三件事——目标是什么、现在到哪一步、凭什么说到了这一步（证据）。

## 2. V 模型：团队顺序的唯一事实

**不是所有任务都开 V 模型**：单点速改、一次问答、纯检索直接做完即收口；
宽面改动 / 高风险 / 需要验收可追溯的任务才开 V 模型。

左腿（分解）→ 右腿（验证），**一左一右配对**，配对的锚点就是完成条件：

| 左腿阶段 | 右腿验证阶段 | 配对锚点（可追溯） |
|---|---|---|
| 需求 | 验收测试 | 需求条目 ↔ 验收用例（逐条对应） |
| 设计 | 集成测试 | 设计的接口/数据流 ↔ 集成路径 |
| 模块分解（契约） | 单元测试 | 模块/函数/签名 ↔ 单元用例 |

- 顺序写进 `team_plan` 的 `stages[].depends_on`（**唯一事实**）：右腿阶段依赖它配对的左腿阶段与实现阶段。
- 末尾**必有一个 `review` 阶段**，依赖全部右腿阶段，只读权责（能跑 test/lint/编译，不改代码）。
- **先算人再铺阶段**：在编 teammate ≤ `limits.team.max_teammates`（默认 6）。骨架（需求/设计/契约评审/实现
  + 三层验证 + 终审）正好 6 人；要加角色就先裁阶段。
- 骨架与成员表见 `$teamwork` 的「V 模型阶段模板」，照抄后按任务改名/裁剪。

## 3. 代码工作：先契约，后实现

1. **契约阶段先行**：定接口 / 签名 / DTO / 错误语义 / 不变式，**写进仓库文件**，不是口头描述。
2. **契约评审通过后才派实现**：`contract_review` 阶段（只读）给出结论前，不派 `impl`。
3. **实现阶段只填契约，不改契约**：发现契约不成立 → 停下来。
4. **契约变更 = 显式 replan**：改 `team_plan`（重建阶段依赖）+ 看板 `decision` 打点（改了什么、哪些阶段返工）。
   契约变更不允许悄悄发生。

## 4. 每阶段收尾（leader 的固定动作）

1. **取回产出**：`jobs_manage(op=fetch, handle=<该阶段 handle>)`。
2. **核对改动事实**：`git diff` / 该阶段的提交与文件——**版本事实归 git**，不凭 teammate 的描述。
3. **汇总到看板**：追加阶段打点（结论 + 证据锚点 + 未决项）；证据改变了目标就改写正文/完成条件。
4. **写里程碑**：`team_milestone(id, content)`，content **由你撰写**（交付了什么 + 证据是什么 + 下一步）。
5. **收这一轮**：`team_retire(role)`（回收作业 + 释放 worktree + 清上下文，teammate 保持在线）。
6. **推进 active seq 并派下一阶段**：依赖边满足才派；同一阶段可并发多派，有共享文件写入的必须串行。

## 5. 测试证据至少三层（缺一层不算验过）

| 层 | 交付物 |
|---|---|
| 单元 / 集成用例 | 可复跑命令 + 结果；覆盖正常路径与边界；修复类改动先红后绿 |
| **性能热点查看** | profile / benchmark / pprof 的**热点与量级**（如 CPU 前 3 名函数及占比、分配次数/耗时量级）；没有量级的性能结论不算证据 |
| **全局冒烟（computer use）** | 把**每个操作都试一遍**：打开 / 点按 / 输入 / 切换 / 滚动 / 关闭 / 恢复——逐个入口点一遍 |

冒烟证据必须写清「**试过哪些操作、哪一步失败**」：操作清单 + 每步结果 + 失败处的截图/日志锚点。
只写「冒烟通过」不算证据。任何一层失败 → 不进收口。

## 6. 失败与收口：以证据为准

- 阶段推不动时**先看证据**（`jobs_manage(op=observe|fetch)`），再决定三选一：
  **重派**（改 `goal` 正文、收窄范围）/ **收窄计划**（`team_plan` 减阶段或换角色）/ **`task_needs_user_decision`**（无法自决）。
- 同一件事最多重派 3 次；到顶就上报，不做无限重试，不靠「再来一轮」碰运气。
- **收口**：右腿三阶段 + `review` 阶段证据齐 → 完成条件**逐条**核对（缺条就说明为何免检）→ `goal_propose_finish`（终态由 gate 判）。
- 提前收手也要留痕：已完成、卡在哪、下一步写进看板打点，再收口或上报。

## 7. 工具面

| 工具 | 你用它做什么 |
|---|---|
| `goal_begin` | 注册目标（标题 + 正文 + 完成条件）——看板从此有正文与完成条件 |
| `goal_update` | 打点：`progress_kind` = milestone/finding/decision/risk + 内容 |
| `goal_status` | 回读看板（栈顶 + 下层状态） |
| `goal_propose_finish` | 提议收口（终态由 gate 判 done/not_done） |
| `$teamwork` | leader 工具面：`team_plan` / `team_dispatch` / `team_join` / `team_milestone` / `team_retire` + `jobs_manage` |
| `task_check_node` / todo | 单代理顺序执行时的打点（与看板打点保持一致，不另立进度真相） |

节奏：`goal_begin` → 写看板 → `team_plan` → 阶段循环（派活 → 收尾读证据 → 打点 + 里程碑 → retire）→ 全绿 → `goal_propose_finish`。
